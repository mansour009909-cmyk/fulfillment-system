# نظام الفولفيلمنت — المراحل 1، 2، 4، 5، فواتير الموردين، الطلبيات الآلية، والتقارير مكتملة

هذا مشروع Next.js + Prisma يغطي **المرحلة 1** (هيكلة المخزون، تحديث الكميات، طباعة الباركود)، **المرحلة 2** (الطلبات: الاستلام، اللقط، التحقق من الاكتمال)، **المرحلة 4** (رسوم العملاء وفواتيرهم)، **فواتير الموردين والمطابقة الذكية** (قسم 6 بالوثيقة، بتصميم فاتورة بأسلوب دفترة — مرجع بصري فقط، بدون أي تكامل خارجي)، **المرحلة 5** (تصنيف الموردين + تخزين مخزون الموردين، قسم 7 و8.3/8.4)، و**الطلبيات الآلية للموردين كاملة** (قسم 8 — حساب "المطلوب"، تتبع حالة الطلبية، تنبيهات الكتب سريعة البيع/الراكدة، وتصدير Excel). المرحلة 3 مؤجَّلة لحين توفر مفاتيح API من سلة.

## طريقة التشغيل محليًا

يحتاج جهازك تثبيت [Node.js](https://nodejs.org) (نسخة 18 أو أحدث).

```bash
# 1) تثبيت المكتبات
npm install

# 2) إنشاء قاعدة البيانات (SQLite محلي، ملف dev.db)
npx prisma migrate dev --name init

# 3) إضافة بيانات تجريبية (رفين وكتابين)
npm run seed

# 4) تشغيل السيرفر المحلي
npm run dev
```

بعدها افتح المتصفح على: http://localhost:3000

النظام الآن يستخدم **Layout كامل** (Sidebar داكن + شريط علوي) مبني على تصاميم Figma/PDF التي زوّدنا بها المستخدم — راجع قسم "نظام التصميم" أدناه.

- الصفحة الرئيسية (`/`): **داشبورد KPI حقيقي** (إجمالي الرفوف، العناوين، النسخ، آخر عمليات المسح) — كل رقم فيه من قاعدة البيانات الفعلية، لا بيانات وهمية.
- `/shelves`: قائمة الرفوف (كانت سابقًا الصفحة الرئيسية).
- صفحة رف (`/shelves/[id]`): خانة نصية تحاكي جهاز الباركود — اكتب/امسح باركود أي كتاب (جرّب `BK-1001` أو أي باركود جديد) وشوف الكمية تتحدث فورًا (+1 لكل مسح). تحتها فورم "إضافة كتاب يدويًا" لإدخال كمية دفعة واحدة بدون مسح متكرر.
- صفحة الكتب (`/books`): **بحث من السيرفر بالعنوان أو الباركود** (ضروري بعد استيراد الكتالوج الحقيقي — 8600+ كتاب)؛ بدون بحث تعرض أحدث 50 فقط. إجمالي الكمية عبر كل الرفوف لكل كتاب، ورابط "+ إضافة كتاب" لإنشاء كتاب بدون تخزينه (تحضيرًا للطباعة).
- صفحات طباعة الباركود (`/shelves/[id]/barcode` و `/books/[id]/barcode`): باركود Code128 كبير قابل للطباعة (`window.print()`).
- `/orders`: قائمة الطلبات بانتظار المراجعة (دفعة حتى 30 طلب، الأقدم أولًا).
- `/orders/picking`: مسار اللقط حسب ترتيب الرفوف — مسح باركود كتاب يوجّهه لأقدم طلب يحتاجه وينقص المخزون المشترك؛ نفاد المخزون يحوّل الطلب تلقائيًا لحالة "قيد التنفيذ".
- `/orders/[id]`: تفاصيل الطلب والتحقق من الاكتمال — مسح باركود الصندوق ثم كل كتاب، رصد "كتاب زائد" فورًا مع إمكانية التراجع، واختيار حجم الطلب قبل "إكمال الطلب".
- `/orders/[id]/barcode`: طباعة باركود الصندوق (= رقم الطلب).
- `/invoices`: إدارة الأسعار العامة والمخصصة لكل عميل، الشحنات المكتملة غير المفوترة، وتوليد فواتير العملاء (زر يدوي بدل جدولة شهرية تلقائية — راجع الملاحظة أدناه).
- `/invoices/audit`: سجل كامل لكل تعديل على الأسعار (القديم/الجديد/من عدّله/متى).
- `/suppliers`: قائمة الموردين والرصيد المستحق لكل واحد — **بحث فوري بالاسم** (بجهة العميل).
- `/suppliers/[id]`: تفاصيل المورد — تنبيه "كتب سريعة البيع" فوري (مخزونها الحالي ≤ نصف مبيعات فترة الحساب — قسم 8.6)، شارتا التصنيف (مهم/عادي، داخلي/خارجي)، عدد كتب كتالوجه، زر "اقتراح طلبية جديدة"، قسم "فواتير الشراء" (بنوعها شراء/تخزين بيع، مع رابط لصفحة متابعة كل الطلبيات الآلية)، قسم "رسوم التخزين" (وحدات تخزين دورية)، وقسم "مخزون المورد بالمستودع" (مخزون بغرض البيع المتبقي، عرض فقط). *(قائمة الطلبيات نفسها انتقلت لصفحة `/supplier-orders` المستقلة تفاديًا للتكرار — الفاتورة الناتجة عن أي طلبية آلية تظهر هنا تلقائيًا بمجرد "تأكيد الوصول".)*
- `/suppliers/[id]/edit`: تعديل اسم المورد وتصنيفه (الأهمية والموقع الجغرافي — قسم 8.3/8.4) وفترة حساب المبيعات (قسم 8.1).
- `/supplier-orders`: **صفحة مستقلة عن الموردين** — كل طلبيات كل الموردين بمكان واحد، النشطة (لسا ما وصلت) أولًا مرتّبة الأقدم فالأحدث، شارة "متأخرة" لكل طلبية تجاوزت المدة المعتادة، **بحث فوري باسم المورد أو رقم الطلبية**. **تتحدّث تلقائيًا كل 10 دقائق** (بجهة العميل، فقط أثناء ما الصفحة مفتوحة بالمتصفح).
- `/suppliers/[id]/orders/[orderId]`: صفحة الطلبية الآلية — Stepper بصري (مقترح→طلب→شحن→وصول)، جدول البنود (الكتاب، مباع بالفترة، الكمية المقترحة/النهائية القابلة للتعديل، إدراج/استبعاد يدوي، شارة "راكد" للكتب بدون أي مبيعات بالفترة)، تنبيه غير مانع لو الكمية الإجمالية أقل من 50، تنبيه "متأخرة" حسب الموقع الجغرافي للمورد، وزر **"تصدير Excel"** (قائمة "المطلوب" النهائية جاهزة للإرسال للمورد — قسم 8.8). عند "تأكيد الوصول" تُدخَل أسعار الوحدة وتُنشأ فاتورة شراء مسودة تلقائيًا تدخل بنفس مسار الاستلام/المطابقة/الاعتماد الحالي — وبعد اعتمادها تُنشأ طلبية مقترحة جديدة تلقائيًا لنفس المورد (قسم 8.5).
- `/suppliers/[id]/invoices/new` و`/suppliers/[id]/invoices/[invoiceId]/edit`: إنشاء/تعديل فاتورة شراء — **جدول بنود تفاعلي بأسلوب دفترة** (منتقي صنف بالبحث بين الكتب الموجودة أو إضافة كتاب جديد، إجماليات تتحدّث لحظيًا)، مع اختيار نوع الفاتورة (شراء عادي / تخزين بغرض البيع). **الفواتير المعتمدة قابلة للتعديل أيضًا** (كمية/سعر/إضافة/حذف بند) — النظام يمنع أي تعديل يخلي المخزون الفعلي يصير سالب، ويصحّح رصيد المورد والمخزون بالفرق تلقائيًا.
- `/receiving`: استلام شحنة — **صفحة عامة واحدة، بدون تحديد مورد مسبقًا**؛ امسح أي كتاب وصل (حتى لو من عدة موردين بنفس الشحنة) ويبني جرد فعلي تراكمي.
- `/receiving/reconcile`: يعرض كل الفواتير المسودة (من أي مورد) اللي تشترك بكتاب واحد على الأقل مع الجرد غير المرتبط — المطابقة تلقائية بحسب الكتب، مو بحسب مورد مُختار مسبقًا.
- `/receiving/reconcile/[invoiceId]`: مقارنة الكمية المتوقعة بالممسوح الفعلي لكل بند (مطابق/فرق/ناقص)، تأكيد الكمية الفعلية بضغطة واحدة، إضافة كتاب وصل فعليًا وغير مدرج بالفاتورة الأصلية، واعتماد الفاتورة (فاتورة الشراء العادية تحدّث رصيد المورد وتضيف المخزون كمشترك؛ فاتورة التخزين بغرض البيع تضيف المخزون كملك للمورد بدون أي تأثير على رصيده).
- `/reports`: تقارير تشغيلية ومالية حقيقية — طلبات مكتملة/بانتظار المراجعة/قيد التنفيذ، إجمالي إيرادات الرسوم، رصيد الموردين المستحق، فواتير عملاء غير مدفوعة، الكتب الأكثر مبيعًا (فترة قابلة للتعديل من `/settings`)، وتنبيه مخزون منخفض عام (كل الكتب، مو مورد واحد). قسم "أداء الموظفين" يظهر "قيد الإنشاء" لأنه يحتاج نظام مستخدمين حقيقي غير موجود بعد.
- `/settings`: إعدادات عامة **حقيقية تؤثر فعليًا على سلوك النظام** (كلها كانت قيم ثابتة بالكود بمرحلة سابقة، صارت قابلة للتعديل ومصدرها الوحيد الآن):
  - اسم المستودع (يظهر بالشريط العلوي).
  - نسبة كتالوج المورد "المهم" المُدرَجة تلقائيًا بالطلبية المقترحة (قسم 8.3).
  - الحدود الدنيا للطلبية (إجمالي/لكل عنوان — قسم 8.2).
  - الفترة الافتراضية لحساب المبيعات (قسم 8.1) — تُطبَّق على أي مورد جديد عند إنشائه، وتحدّد نطاق تقرير "الأكثر مبيعًا" بصفحة `/reports`.
  - مدة تنبيه تأخير الطلبية للموردين الداخليين/الخارجيين (قسم 8.4) — كانت مكرَّرة بثابت بملفين منفصلين، توحّدت بمصدر واحد.

  قسم "إدارة المستخدمين والصلاحيات" يظهر "قيد الإنشاء" لأنه يحتاج نظام تسجيل دخول حقيقي غير موجود بعد.
- `/clients`, `/integrations`: صفحات "قيد الإنشاء" — موجودة بالـ Sidebar لإظهار الهيكل الكامل للنظام، لكن غير مبنية وظيفيًا بعد (تُبنى تباعًا بالمراحل القادمة).

## نظام التصميم

مبني حسب تصاميم PDF زوّدنا بها المستخدم (24 + 5 صفحة تغطي كل المراحل). العناصر المشتركة:

```
components/layout/AppLayout.js  → يغلّف كل صفحة (Sidebar + Topbar)
components/layout/Sidebar.js    → روابط التنقل، قسم "المخزون" قابل للتوسيع
components/layout/Topbar.js     → معلومات المستخدم + التنبيهات + المستودع
components/ui/Card.js           → بطاقة بيضاء بحواف دائرية وظل خفيف
components/ui/Badge.js          → شارة حالة ملوّنة (success/warning/danger/info)
components/ui/KpiCard.js        → بطاقة رقم/إحصائية بأيقونة
components/ComingSoon.js        → قالب موحّد للأقسام غير المبنية بعد
```

الألوان المخصصة (`tailwind.config.js`): `sidebar` (كحلي داكن) و`sidebar-hover`. الأيقونات من `lucide-react`. الخط `IBM Plex Sans Arabic` عبر `next/font/google`.

**مبدأ مهم:** لا تضف بيانات وهمية (أرقام/أسماء) في أي صفحة تدّعي أنها حقيقية — أي قسم بياناته غير موجودة بعد بقاعدة البيانات يُعرض كصفحة "قيد الإنشاء" عبر `ComingSoon`، مو بأرقام مصطنعة.

لمعاينة قاعدة البيانات بشكل مرئي: `npm run prisma:studio`

**ملاحظة تقنية:** `ShelfStock` له مفتاح فريد مركّب `(shelfId, bookId, ownership, clientId)`، و`clientId` قد يكون `null`. Prisma لا يسمح بـ `null` داخل `where` لمفتاح فريد مركّب، لذلك كل نقاط البحث عن مخزون مشترك (`scan.js`, `stock.js`, `seed.js`) تستخدم `findFirst` بدل `findUnique` على المفتاح المركّب — التزم بنفس النمط عند إضافة أي منطق جديد يبحث في `ShelfStock`.

**ملاحظات تبسيط بالمرحلة 4:** توليد الفاتورة الشهرية زر يدوي (بدل جدولة تلقائية، لأن ما فيه بنية cron بالمشروع). رسوم الشحن قيمة ثابتة قابلة للتعديل (بدل "تكلفة فعلية" من شركة شحن حقيقية). رسوم التخزين قابلة للتسعير لكن ما تُحتسب فعليًا على أي طلب لأن المخزون الخاص بالعملاء (private inventory) نفسه غير مبني بعد.

**ملاحظات تبسيط بفواتير الموردين:** الاستلام صفحة عامة واحدة (`/receiving`) — لا تحديد مورد أو فاتورة وقت المسح؛ المطابقة تبحث تلقائيًا عن كل الفواتير المسودة (من أي مورد) اللي تشترك بكتاب واحد على الأقل مع الجرد غير المرتبط، ويختار الموظف الفاتورة الصحيحة يدويًا من المرشَّحات (تُختبر هذي الآلية فعليًا: مورّدان مختلفان بشحنة واحدة ظهرا كمرشَّحين منفصلين بنجاح). إضافة المخزون بعد الاعتماد تحتاج اختيار رف واحد لكل الفاتورة (بدل توزيع ذكي متعدد الرفوف). تصنيف الموردين (مهم/عادي)، الطلبيات الآلية الدورية (قسم 8)، والتخزين لدى المورد (قسم 7) — مؤجَّلة للمرحلة القادمة.

**ملاحظة حول تصميم فواتير الموردين:** جدول بنود الفاتورة (بحث/إضافة صنف + إجماليات لحظية) مبني بأسلوب مستوحى بصريًا من واجهة دفترة (Daftra) — **مرجع تصميم/تجربة استخدام فقط**. لا يوجد أي تكامل، اتصال، أو اعتماد تقني على دفترة كنظام محاسبي خارجي (وثيقة المتطلبات قسم 6.1 تمنع هذا صراحة) — كل البيانات والمنطق داخلي بالكامل بهذا المشروع.

**ملاحظات تبسيط بالمرحلة 5 (تصنيف وتخزين الموردين):**
- تخزين المورد بنوعيه (بسيط وبغرض البيع) يشترك بمفهوم واحد لرسوم التخزين الدورية (`SupplierStorageUnit`) — لا يوجد بعد نظام فوترة دوري تلقائي للموردين (لا "SupplierInvoice" مواز لـ`ClientInvoice`)، الفوترة الفعلية مستقبلية.
- تخزين المورد بغرض البيع (قسم 7.2) يُسجَّل كمخزون خاص بالمورد (`ShelfStock.ownership = SUPPLIER`) — **منفصل كليًا عن مسار لقط طلبات العملاء** (`pick-scan.js`/`picking.js` يتعاملان مع المخزون المشترك فقط ولا يمسّان هذا النوع إطلاقًا)، لأن بيعه يتم بالجملة بمسار منفصل تمامًا، بناءً على توجيه صريح من المستخدم. **بدون أي حساب عمولة أو تسوية مالية تلقائية بالنظام إطلاقًا** — العمولة تُتفق عليها وتُدار بالكامل خارج النظام بين الشركة والمورد.

**كتالوج الكتب↔الموردين واستيراد المخزون الحقيقي:** `Book.supplierId` يمثّل "المورد الافتراضي" لكل كتاب — أساس حساب "المطلوب" بالطلبيات الآلية. تم استيراده من ملف مخزون منتجات خارجي حقيقي (نفس الملف المستخدم مع سكيل `supplier-inventory-report` لحساب مستحقات الموردين) عبر `scripts/read_inventory_xlsx.py` (يطبّق نفس قواعد تطبيع أسماء الموردين بالسكيل — بدون منطق الضريبة/الأرصدة غير ذي الصلة) ثم `scripts/import-catalog.js` (استيراد هوية فقط — لا يمس المخزون أو الأسعار). النتيجة: 8654 كتاب عبر 128 مورد حقيقي. لإعادة الاستيراد أو تحديثه بملف أحدث:
```bash
python scripts/read_inventory_xlsx.py <ملف.xlsx> scripts/catalog_import.json
node scripts/import-catalog.js
```

**ملاحظات تبسيط بالطلبيات الآلية للموردين (قسم 8):**
- التصنيف (مهم/عادي) يحدّد فقط أي الكتب تُدرَج تلقائيًا بالاقتراح (النسبة الأعلى مبيعًا للمورد "المهم"، ولا شيء مُدرَج تلقائيًا للمورد "العادي" — يختار الموظف يدويًا). النسبة قابلة للتعديل من `/settings` (افتراضيًا 80%).
- "الطلبية" (`SupplierOrder`) نموذج خفيف يغطي فقط ما قبل الوصول الفعلي (مقترح→طلب→شحن→وصول)؛ عند "تأكيد الوصول" تتحول تلقائيًا لفاتورة شراء مسودة عادية (`PurchaseInvoice`) وتدخل بنفس مسار الاستلام/المطابقة/الاعتماد الموجود من قبل — لا ازدواجية بالمنطق.
- تنبيه "الكتب الراكدة" (بدون مبيعات بالفترة) يظهر كشارة تحذيرية داخل جدول بنود الطلبية المقترحة (بدل شاشة/تدفق منفصل) — الموظف يقرر يدويًا عبر مربع الإدراج نفسه.
- التصدير حاليًا Excel فقط (`exceljs`) — PDF لكل طلبية مؤجَّل (لم يُطلب صراحة، ونفس ملف Excel يغطي الحاجة العملية للإرسال للمورد).
- نسبة "80%" وحدود الطلبية الدنيا صارت مُخزَّنة بـ`SystemSetting` وتُقرأ ديناميكيًا بدل ثوابت بالكود — قابلة للتعديل من `/settings`.

## تطبيق الجوال (Flutter) + نظام تسجيل الدخول (إداري/موظفين/عميل/مورد)

بطلب من المستخدم، رُبط تطبيق جوال Flutter منفصل (كان مبنيًا أصلًا لتجهيز طلبات سلة عبر باك-إند خاص به مع تكامل سلة مباشر — مشروع `salla-warehouse-picking` بمجلد مستقل) **مباشرة** بهذا النظام، بدون أي وسيط: تُجوهل الباك-إند القديم وتكامل سلة بالكامل، ويتكلم التطبيق مع Next.js API هنا عبر `/api/mobile/**`. **تقسيم وظيفي واضح**: الجوال أداة المسح الفعلي بالمستودع فقط (دفعات لقط + تحقق نهائي من الصندوق)، والويب يبقى للإدارة الكاملة (الطلبات، الفواتير، الموردين، التقارير، الإعدادات) — صفحات اللقط/التحقق بالويب (`/orders/picking`, `/orders/[id]`) بقيت بدون حذف كخيار احتياطي.

**"الدفعة" (`PickingBatch`) طبقة رقيقة فوق `Order`/`OrderItem` الموجودين** (لا تكرار بيانات، خلافًا للباك-إند القديم): تسحب أقدم 30 طلب `PENDING_REVIEW` ما دخل دفعة من قبل، توزّعها على أرقام صناديق متسلسلة، وتبني مسار مشي بالرفوف. المسح يستدعي نفس منطق اللقط الحالي (`lib/orderFulfillment.js` — استُخرج من `pick-scan.js`/`box-scan.js`/`verify-scan.js`/`undo-verify.js`/`complete.js` الأصليين ليُستخدم من الويب والجوال معًا بدون تكرار)، مقيّدًا بطلبات الدفعة ومرتّبًا برقم الصندوق بدل تاريخ الإنشاء. "تخطّي" (نفذ المخزون) يسجَّل بحقل جديد `OrderItem.quantityShort` بدل تحويل الطلب فورًا لـIN_REVIEW.

**تسجيل الدخول ثلاثة حسابات منفصلة تمامًا:**
1. **موظف بالجوال فقط** (`Employee`، رقم سري PIN) — لتنفيذ عمليات اللقط/التحقق ميدانيًا. توكن HMAC-SHA256 موقّع (`lib/mobileAuth.js`)، بدون أي حزمة JWT خارجية. صفحة إدارة: `/employees` (إضافة موظف، تعطيل، إعادة تعيين PIN) + إحصائية "أداء الموظفين" حقيقية بصفحة `/reports` (عدد الطلبات المكتملة لكل موظف، عبر `Order.fulfilledByEmployeeId` الذي يُسجَّل تلقائيًا عند إكمال الطلب من الجوال).
2. **حساب إداري واحد مشترك** للوحة التحكم الرئيسية بالويب (اسم مستخدم + كلمة سر، مخزَّنة بـ`SystemSetting`) — يحمي كل صفحات الإدارة. تغييره من قسم "حساب الإدارة" بصفحة `/settings`.
3. **بوابتا عميل/مورد خارجيتان جديدتان** (`/portal/client`, `/portal/supplier`) — كل عميل/مورد يسجّل دخول ببريد وكلمة سر خاصة فيه (`Client.email/passwordHash`, `Supplier.email/passwordHash`) ويشوف طلباته/فواتيره فقط، للقراءة فقط. بيانات الدخول تُعيَّن من الإدارة فقط (لا تسجيل ذاتي) — من صفحة `/clients` (أُعيد بناؤها بالكامل، كانت `ComingSoon` فاضية) وقسم "بوابة المورد" بصفحة تفاصيل المورد.

جلسات الويب الثلاثة محميّة بكوكي `httpOnly` موقّع (`lib/webAuth.js`) عبر **Web Crypto API فقط** (`crypto.subtle`، بدون `node:crypto`/`Buffer`) — نفس الكود يشتغل بـ`middleware.js` (Edge runtime) وبمسارات API (Node runtime) بدون فرق. `middleware.js` بجذر المشروع يفرض الفصل: `/portal/client/**` يتطلب دور CLIENT، `/portal/supplier/**` يتطلب SUPPLIER، وكل شيء آخر يتطلب ADMIN — كل مسار `/api/mobile/**` مستثنى بالكامل (مصادقته بالتوكن منفصلة تمامًا عن الكوكي).

**تجزئة الأرقام السرية/كلمات السر:** `lib/crypto.js` — `scrypt` المدمجة بـNode (salt عشوائي + hash)، بدون `bcrypt` أو أي حزمة خارجية.

**بيانات افتراضية عند أول `npm run seed`:** حساب إداري `admin` / `admin123` (يتغيّر فورًا من `/settings`)، وموظف جوال افتراضي "المشرف" برقم سري `1234`.

الملفات الرئيسية: `prisma/schema.prisma` (`Employee`, `PickingBatch`, `PickingBatchOrder`, `Order.fulfilledByEmployeeId`, `OrderItem.quantityShort`, `SystemSetting.adminUsername/adminPasswordHash`, `Client/Supplier.email/passwordHash`) · `lib/{crypto,mobileAuth,webAuth,orderFulfillment,pickingBatch}.js` · `middleware.js` · `pages/api/mobile/**` (دفعات + لقط + تحقق) · `pages/{login,portal/client,portal/supplier,employees,clients}` وواجهاتها البرمجية.

## النشر الإنتاجي (Railway + PostgreSQL)

النظام صار منشورًا فعليًا على الإنترنت (Railway) بدل التشغيل المحلي فقط — لازم عنوان HTTPS دائم لتسجيل تطبيق سلة لاحقًا، ولحل مشاكل الشبكة المحلية (فايروول/راوتر) مع تطبيق الجوال نهائيًا.

**الرابط الإنتاجي:** `https://fulfillment-system-production.up.railway.app`

**قاعدة البيانات تحوّلت من SQLite إلى PostgreSQL** (خدمة Postgres على نفس مشروع Railway) — التطوير المحلي وInline والإنتاج يشتركون بنفس القاعدة الفعلية عبر `DATABASE_URL`:
- محليًا (`.env`): يستخدم الرابط **العام** لقاعدة Postgres (`nozomi.proxy.rlwy.net:...`) لأن الجهاز المحلي ما يوصل للشبكة الداخلية لـRailway.
- على Railway (خدمة `fulfillment-system`): `DATABASE_URL` مرتبط عبر **Variable Reference** بالرابط **الداخلي** لخدمة Postgres (أسرع وأأمن، ما يمر بالإنترنت العام).
- `AUTH_SECRET` مُعرَّف بشكل منفصل بكل بيئة (قيمة مختلفة محليًا عن الإنتاج) — لا يُشارَك بين البيئتين.

**migrations القديمة (SQLite) محفوظة محليًا فقط** بمجلد `prisma/migrations_sqlite_backup/` (مستبعَد من Git) للرجوع إليها عند الحاجة — استُبدلت بمigration واحدة جديدة متوافقة مع Postgres (`prisma/migrations/20260806072100_init/`).

**سكربتات `package.json` المعدَّلة للنشر:**
```json
"postinstall": "prisma generate",
"start": "prisma migrate deploy && next start"
```
`postinstall` يضمن توليد Prisma Client بعد كل `npm install`، و`start` يطبّق أي migration جديدة تلقائيًا قبل تشغيل السيرفر — تدفع تحديث لـGitHub وRailway ينشره وينفّذ المigrations تلقائيًا بدون أي تدخل يدوي.

**تنبيه أمان:** الوصول العام لقاعدة Postgres (Public Access) مفعّل حاليًا عشان التطوير المحلي يقدر يوصلها — كلمة السر طويلة وعشوائية (وليّدها Railway نفسه)، لكن لو احتجتوا تعطيله لاحقًا (بعد نقل التطوير لبيئة تقدر توصل الشبكة الداخلية)، فعّلوه/عطّلوه من تبويب Settings بخدمة Postgres.

## الخطوات القادمة (حسب خطة المراحل)

المراحل 1، 2، 4، 5، فواتير الموردين (قسم 6)، الطلبيات الآلية كاملة (قسم 8)، والتقارير مكتملة. المتبقي كلاهما يحتاج مفاتيح API حقيقية من طرف خارجي (نفس وضع سلة) — مؤجَّلان لحين توفرها:

1. **المرحلة 3 (تكامل سلة الفعلي)**: تحتاج مفاتيح API من تطبيق سلة (تطبيق خاص لا يحتاج موافقة سلة، لكن يحتاج إنشاءه من لوحة شركاء سلة `salla.partners`). **رابط الموقع/إعادة التوجيه المطلوب عند إنشاء التطبيق بلوحة سلة صار متوفرًا فعليًا**: `https://fulfillment-system-production.up.railway.app` (راجع قسم "النشر الإنتاجي" أعلاه). لما تتوفر المفاتيح: تكامل Salla API لسحب الطلبات فعليًا بدل بيانات seed، ومزامنة حالتها تلقائيًا. (حسابات العملاء وبوابتهم ونظام تسجيل الدخول الإداري/الموظفين مبنية فعلًا — راجع القسم أعلاه.)
2. **تكامل شركات الشحن (قسم 4.6)**: توليد بوليصة فعلية + تتبع شحن + تكلفة فعلية بدل القيمة الثابتة — تحتاج مفاتيح API حقيقية من شركة شحن (سمسا/أرامكس/بريد SPL أو غيرها).

راجع جدول الكيانات (قسم 9) في وثيقة المتطلبات — كل الجداول المذكورة هناك تُبنى تباعًا بنفس أسلوب `schema.prisma` هذا.
